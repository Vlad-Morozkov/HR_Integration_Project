# PROJECT CONTEXT: HR Hiring System

## 1. Project Overview:

A pet project called "HR Hiring System" to demonstrate system integration.
The Frontend consists of two forms (Candidate and HR), located in the same browser tab. Switching between forms is performed using a mode switcher.
The Backend is responsible for API business logic and database operations.

    Technologies:
        Python 3.x
        FastAPI + SQLAlchemy + Uvicorn
        Streamlit
        SQLite (local development)/PostgreSQL (production)
        python-dotenv
        Gmail SMTP (sending email notifications)

    API_URL = "http://127.0.0.1:8000"
    API title = "HR Hiring System API"
    API version = "1.1.0"

## 2. Main Process:

The Candidate submits an application, which the system saves in the Applications table. Applications are displayed to the HR specialist, who makes a decision: "Hire" or "Reject".

    If "Hire":
        The application status becomes "Hired".
        The associated position is marked as occupied (is_free = False).
        An email notification about the hire is sent to the candidate.
        A notification to prepare a workplace is sent to the Support Email.

    If "Reject":
        The application status becomes "Canceled".
        The record is retained in the database for history (Soft Delete).
        An email notification about the rejection is sent to the candidate.
        The candidate can reapply for the same position.

    Only applications with the "New" status can be processed.
    After the status changes to "Hired" or "Canceled", further status changes are unavailable.

## 1. Candidate Form Logic

Fields (all required):

    full_name                       (String)
    email                           (String)
    position_id                     (Dropdown: retrieves pos_name from the Positions table, but sends id to the server)
    educ                            (String)
    experience                      (String)
    birth_date                      (Date)

UI Actions:

    "Fill with test data" button.
        Action: requests demo data from the server via GET
            /api/demo-application?lang=en or ?lang=ru.
        The form is populated with data based on the selected language.
        position_id is selected from the available positions in the dropdown.

    "Submit Application" button.
        Validates required fields.
        Validates the email format on the frontend.
        Checks that the birth date is strictly earlier than the current date (automatically populated).
        Sends a POST request to the server with a JSON body.

Frontend Validation:

    If a required text field is empty or contains only whitespace:
        Display a message asking the user to fill in the field.

    If the email does not match the validated format:
        Display the message "Please enter a valid email address."

    If birth_date is today's date or in the future:
        Display the message "Birth date cannot be today or in the future."

    If a connection error occurs:
        Display a message indicating that the HR Hiring System cannot be reached.

Server Response Handling:

    If HTTP 201 Created:
        Display the message "Data submitted successfully."

    If HTTP 409 Conflict:
        Display the message "You have already applied for this position."

    If HTTP 422 Unprocessable Entity:
        Display a message indicating a data submission error.

    For other errors:
        Display an error message with the HTTP status code.

## 2. Backend Logic & Database Schema

ID generation: UUIDs are generated by the backend when records are created.

Table: Positions

    id          (UUID, Primary Key)
    pos_name    (String)
    is_free     (Boolean, default True)

Table: Applications

    id          (UUID, Primary Key)
    position_id (UUID, Foreign Key referencing Positions.id.
                 The UI displays pos_name, but position_id is stored in the database)
    app_date    (DateTime, application creation date and time in UTC)
    educ        (String)
    experience  (String)
    full_name   (String)
    email       (String, normalized: whitespace is removed, letters are converted to lowercase)
    birth_date  (Date)
    status      (String: "New", "Hired", "Canceled")

The API response for Applications also contains:

    position_name (String, position name from the Positions table)

## 2.1 Endpoint Logic: POST /api/applications

    Retrieve data from the JSON request body.

    Validate position_id:
        Convert the UUID to its string representation.
        Find the corresponding record in the Positions table.

    If the position is not found:
        Return HTTP 404 Not Found: "Position not found."

    Normalize email:
        Remove leading and trailing whitespace.
        Convert the email to lowercase.

    Find an application in the Applications table where:
        email matches the normalized email
        AND position_id matches the received position_id
        AND status equals "New" OR "Hired".

    If such an application is found:
        Return HTTP 409 Conflict:
        "You have already applied for this position."

    Otherwise:
        Create a new record in Applications:
            - Generate a UUID id.
            - Record the current date and time in app_date (UTC).
            - Save the form data.
            - Save the normalized email.
            - Set status = "New".

        If the previous application has the status "Canceled":
            Retain the old record for history.
            Create a new record with a new UUID.

        Return HTTP 201 Created.

    Additional handling:
        On IntegrityError, perform a rollback and return HTTP 409 Conflict.
        On an unexpected error, perform a rollback and return HTTP 500 Internal Server Error.

## 2.3 Endpoint Logic: POST /api/reset-demo

    1. Delete all existing records from the Applications table.
    2. Delete all existing records from the Positions table.
    3. Create three demo positions:
        - Senior Backend Developer
        - Frontend Engineer
        - HR Manager
    4. Create six demo applications:
        - Three English examples.
        - Three Russian examples.
    5. Set is_free = False for Frontend Engineer because one of the demo applications for this position has the status "Hired".
    6. Save the changes to the database.
    7. Return HTTP 200 OK with the number of created positions and applications.
    8. The frontend refreshes the interface and displays a message confirming that the demo data was loaded successfully.

    Important:
        The endpoint deletes and recreates positions rather than only resetting their availability.
        Existing applications and positions are deleted when demo data is reset.

## 2.4 Implemented API Endpoints

    GET /api/positions
        Returns a list of positions with the fields id, pos_name, is_free.

    POST /api/positions
        Creates a new position.
        Accepts JSON containing pos_name and is_free.
        Returns HTTP 201 Created.

    GET /api/applications
        Returns a list of applications together with position_name.
        Supports optional parameters:
            position  (search by position name, partial match)
            full_name (search by full name, partial match)

        Email filtering is performed on the frontend.

    POST /api/applications
        Creates an application with validation of required fields and duplicates.

    PATCH /api/applications/{app_id}/status
        Changes the application status to "Hired" or "Canceled".
        Processes only applications with the status "New".
        When hiring, marks the associated position as unavailable.
        Attempts to send an email to the candidate and, when hiring, to Support.
        Returns information about the status and email-sending results.

    PATCH /api/applications/{app_id}/email
        Updates the email of an existing application.
        Removes leading and trailing whitespace and converts the email to lowercase.
        Checks for the presence of the "@" character.
        Returns HTTP 404 if the application is not found.
        Returns HTTP 422 if the email is invalid.
        Returns HTTP 409 Conflict on IntegrityError.

    POST /api/reset-demo
        Deletes and recreates demo positions and demo applications.

    GET /api/demo-application?lang=en|ru
        Returns the first demo example for the selected language.
        Supported lang values: "en" and "ru".
        If the language is unsupported, returns HTTP 400 Bad Request.

## 3. HR Form Logic

    Header block:

        "Refresh" button to refresh the interface and discard unsaved email changes.

    Filter block:
        Position filter (by position name).

        "Clear filters" button to clear filters.

            Full Name

            Checkbox for selecting an application.

        Email column:

            After a change, the frontend sends a PATCH request to update the email.

    Duplicate email validation during editing:
        If an email is already used by an active application for the same position:
            - Display a warning.
            - Display the conflicting email as a clickable element.
            - Clicking it copies the email to the clipboard if the browser permits copying.
            - Display a hint that the Refresh button discards unsaved email changes.
            - Disable Hire and Reject for the selected application until the conflict is resolved.

    Additional validation before hiring:
        If another candidate with the same email already has the status "Hired":
            Display the notification "This candidate is already hired".
            The Hire button remains available only if all other application-processing conditions are met.

    Support Email block:
        Field for the Support email address.
        Used when hiring a candidate to send a notification about preparing a workplace.

    Positions block:
        Displays the list of positions.

            Position
            Available

        If a position is available:
            Display a green check mark "✔".

        If a position is unavailable:
            The Available cell remains empty.

        New Position field:
            Enter the name of a new position.

        Add Position button:
            Sends a POST request to create a position.

    Actions block:
        Hire and Reject buttons for the selected application.
        The buttons are disabled if:
            - Exactly one application is not selected.
            - The application status is not "New".
            - The email is invalid.
            - An email conflict has been detected for the selected application.

    Notifications:
        Successful position creation is displayed after the Add Position action.
        Successful email updates are displayed after changing the email.
        Successful hiring is displayed after the Hire action.

## 3.2 "Reset & Load Demo Data" Button Logic

    1. The frontend sends a POST request to /api/reset-demo.
    2. The backend deletes all existing applications.
    3. The backend deletes all existing positions.
    4. The backend creates three demo positions.
    5. The backend creates six demo applications in English and Russian.
    6. The backend sets is_free = False for Frontend Engineer.
    7. The backend returns a success message.
    8. The frontend refreshes the interface and displays a notification confirming that the demo data was loaded successfully.

## 3.3 "Refresh" Button Logic

    When clicked:
        Increment the table editor version to discard unsaved changes.
        Rerun the Streamlit interface.

    When loading applications:
        Send a GET request to /api/applications with the following parameters:
            position  = applied position filter
            full_name = applied full name filter

        After receiving the response:
            If an email filter is specified:
                Filter the retrieved applications on the frontend by partial email match, ignoring case.

            If applications are found:
                Display them in the table.

            If no applications are found:
                Display the message "No applications found."

            If a request error occurs:
                Display a request error message.

## 3.4 Row Selection and Actions Logic

    If the user selects one application:
        Check the application status.
        Check whether the email is valid.
        Check for an email conflict.
        If status = "New", the email is valid, and there is no conflict:
            Enable the Hire and Reject actions.

    If the user has not selected any applications:
        Display the hint "Select one application."
        Disable Hire and Reject.

    If the user selects more than one application:
        Display the warning "Please select only one application."
        Disable Hire and Reject.

    If the application status is not "New":
        Disable Hire and Reject.

## 3.5 Email Editing Logic

    HR edits the email directly in the Applications table.

    Frontend:
        Compares the modified email with the original value.
        Checks whether the same email is used by another active application for the same position.
        Applications with the status "New" or "Hired" are considered active.

    If a conflict is detected:
        Do not save the change.
        Display a warning with the conflicting email.
        Allow the email to be copied by clicking it.
        Suggest clicking Refresh to discard the change.

    If there is no conflict:
        Send a PATCH request to /api/applications/{app_id}/email.

    If HTTP 200 OK:
        Save the updated email.
        Refresh the interface.
        Display the message "Email updated successfully."

    If HTTP 409 Conflict:
        Display an email conflict warning if the response indicates a conflict with an active application.

    If HTTP 422 or another error occurs:
        Display an email update error message.

## 3.6 "Reject" Button Logic

    Retrieve the selected application's email, taking any edits into account.

    Validate the email on the frontend:
        If the email is invalid:
            Disable the Reject button.

    If the email is valid:
        Send a PATCH request to /api/applications/{app_id}/status with JSON:
            status = "Canceled"
            email  = candidate email

    Backend:
        Checks whether the application exists.
        Checks that the current application status is "New".
        Changes the status to "Canceled".
        Saves the changes to the database.
        Attempts to send an email to the candidate via Gmail SMTP.

    Email subject:
        "Application update"

    Email body:
        "Sorry, your application is not a fit for us. Have a good day."

    If HTTP 200 OK:
        The frontend refreshes the interface.
        Displays the message "Application rejected."

    If the request fails:
        The frontend displays an error message for Reject.

    Important:
        If email sending fails, the application status change may already have been saved.
        A successful API response does not mean that the email was necessarily delivered.

## 3.7 "Hire" Button Logic

    Retrieve the selected application's email, taking any edits into account.
    Retrieve support_email from the Support Email field.

    Validate the candidate's email:
        If the email is invalid:
            Disable the Hire button.

    Check that the application has the status "New".
    Check that there is no email conflict for the selected application.

    Send a PATCH request to /api/applications/{app_id}/status with JSON:
        status        = "Hired"
        email         = candidate email
        support_email = Support email address

    Backend:
        Checks whether the application exists.
        Checks that the application status is "New".
        Finds the associated position.
        Changes the application status to "Hired".
        Sets is_free = False for the associated position.
        Saves the changes to the database.

    Email to the candidate:
        Subject = "Congratulations! You are hired"
        Message = "Congratulations, you are hired! Come work with us."

    Email to Support (if support_email contains "@"):
        Subject = "New employee hired"
        Message = "New employee [full_name] hired. Please prepare a workplace."

    Gmail SMTP:
        Uses SMTP_SSL on smtp.gmail.com:465.
        Credentials are taken from environment variables:
            GMAIL_ADDRESS
            GMAIL_APP_PASSWORD

    Backend returns:
        application_id
        status
        candidate_email_sent
        support_email_sent (when hiring)

    If email sending fails:
        The backend logs the error.
        The application status may remain "Hired".
        The frontend displays a notification that the status was changed successfully, but this does not confirm email delivery.

    If HTTP 200 OK:
        The frontend refreshes the interface.
        Displays the message "Application hired."

    If the request fails:
        The frontend displays an error message for Hire.
