## Решение

Постепенно преобразовать существующее приложение в модульный монолит: маршруты FastAPI → прикладные сервисы → узкие функции доступа к данным и адаптеры SMTP/Cal.com. Сохранить FastAPI, Streamlit, SQLAlchemy, текущие точки входа и API. Перед каждым переносом зафиксировать существенное поведение тестами; исправления найденных ошибок делать отдельными изменениями с новым ожидаемым результатом.

## С чего начать реализацию

1. **P0 — подготовка:** исправить некорректный `.gitattributes` отдельным изменением, зафиксировать версии работающего окружения и безопасный тестовый запуск. Сохранить независимые локальные правки пользователя.
2. **P1 — ключ:** заменить опубликованный ключ, убрать все три резервных литерала, исключить `.streamlit/secrets.toml` из Git и проверить авторизацию. Публичную почту сохранить.
3. **P2 — исходные контракты:** добавить проверки API, сценариев найма/бронирования/reset и переключения RU/EN на изолированных данных.
4. **P3–P8 — выделение модулей:** конфигурация/БД/схемы → SMTP и Cal.com → сервисы → routers → единый frontend-клиент → экраны.
5. **F1–F6 — отдельные исправления:** RU Candidate, конкурентные изменения БД, согласование Cal.com/БД, reset, timezone, служебный запуск. Задачи можно поднимать раньше по зависимостям и риску; они не должны маскироваться под механическое перемещение файлов.

## Границы и договорённости

- Публичный контактный email допустим по решению владельца. `GMAIL_APP_PASSWORD`, API-токены, webhook secret и пароль в URL БД — секреты.
- Общий `INTERNAL_API_KEY` защищает соединение серверного Streamlit с API. Права посетителей HR-интерфейса требуют отдельного решения; выбор HR в меню не является авторизацией.
- Сохранить реальные статусы **`New`, `Hired`, `Canceled`** и явную семантику `force=True`; не вводить другое правило найма без отдельного изменения.
- Не вызывать реальные demo reset, SMTP и Cal.com при проверке рефакторинга. Изменение схемы проверять на отдельной БД/копии.
- Папка Windows: `C:\Users\79000\GitHub\HR_Integration_Project`. На момент анализа HEAD совпадал с GitHub; существовали незакоммиченные `.gitignore` и `Plan.md` для sidebar. Эти изменения не включать автоматически в коммиты рефакторинга.
- Рабочие deployment-настройки, текущие значения секретов, версия Python именно в `.venv`, число workers и реальная схема PostgreSQL не проверялись. Список точечных проверок приведён в [06](06-sources-and-decisions.md).

## Когда рефакторинг можно считать завершённым

Ключ не хранится в коде; API-контракты и сценарии проверяются автоматически; `main.py` и `frontend.py` служат точками сборки; запросы UI проходят через один клиент; прикладная операция имеет одного владельца транзакции; сбои SMTP/Cal.com не теряют сведения для восстановления; изменения БД имеют проверяемые миграции; запуск и откат описаны и воспроизводимы. Конкретные проверяемые критерии разбиты по этапам в [01](01-strategy-and-roadmap.md) и [05](05-testing-and-delivery.md).
